# AGENTS.md

Kitodo.Presentation: a TYPO3 extension (extension key `dlf`, PSR-4 `Kitodo\Dlf\` → `Classes/`). PHP 8.2–8.5, TYPO3 12.4 or 13.4. Apache Solr is the search backend (not needed for unit tests).

## PHP

- Install test dependencies: `composer install-via-docker -- -t 12.4` or `-- -t 13.4`
- Unit tests (Docker): `composer test:unit`; locally: `composer test:unit:local` (or `vendor/bin/phpunit -c Build/Test/UnitTests.xml`, add `--filter <name>` for one test)
- Functional tests **only run in Docker** (need MariaDB/Solr containers): `composer test:func` or `Build/Test/runTests.sh -s functional`; `-w` for watch mode. Options: `Build/Test/runTests.sh -h`
- Fixtures for functional tests live in `Tests/Fixtures/`; use distinct, greppable 9-digit `uid`s (`rand(100000000, 999999999)`)
- Static analysis: `composer phpstan` (hardwired to `.github/phpstan_13.4.neon`; CI runs one neon per TYPO3 version, `.github/phpstan_12.4.neon` included)
- Code style: `composer php-cs-fixer:check` / `composer php-cs-fixer:fix`

## Local (no-Docker) test installation

**Automated:** `Build/Demo/setup-demo.sh` builds the whole site end-to-end (composer install, `typo3 setup`, database seed, caches) and prints the URLs. It bakes in every workaround below and additionally generates a small **local** sample document (METS + 3 placeholder pages drawn with PHP GD) served on its own static port, so the PageView viewer works fully offline with the form pre-filled. Options: `--dir`, `--port`, `--branch`, `--user`, `--password`, `--style` (viewer theme, one of the `Build/Demo/styles/<name>/` directories, default `aurora`), `--serve` (start both servers in the foreground), `--no-sample`. It is idempotent. Use the manual steps below only to understand / tweak a specific part.

The demo page frames each viewer plugin (`dlf_pageview`, `dlf_navigation`, `dlf_pagegrid`, `dlf_metadata`, `dlf_toolbox`) in a labelled box and offers a floating **style selector** to switch the whole viewer look at runtime. Styles are the **subdirectories** of `Build/Demo/styles/`; each one is a theme that must contain its main stylesheet `<name>.css` and may carry further assets (images, scripts, ...) alongside it. Add a new directory there and it is picked up automatically (copied verbatim into the site, added as a `<option>`). `Build/Demo/assets/` holds helper CSS that is copied alongside the styles but is *not* a switchable style (the widget's own `demo-widgets.css`). The page wraps the plugin content in `<div id="main">` and addresses each plugin's fsc frame with `#main .frame:has(<dlf element>)`. The active stylesheet is **not** an `includeCSS` (TYPO3's asset pipeline concatenates those into one `merged-*.css`); the page's inline script manages its own `<link id="dlf-demo-css">` and retargets it at `kitodo-demo/<name>/<name>.css` when the selector changes. The choice is remembered in `localStorage` (`kitodo-demo-style`), so it survives the full page reloads that viewer navigation (thumbnails, page controls) triggers; the `<option selected>` from `--style` is only the default for a first visit.

A live TYPO3 site with this extension can be installed outside Docker. Reference working setup: TYPO3 13.4, PHP 8.5 (Homebrew) with `composer config platform.php 8.4.99` in the site project (pins the platform so composer does not depend on the Homebrew PHP version), SQLite as the database. The extension is pulled in as a `path` repository (symlink) so the local checkout is used.

Steps (site dir, e.g. `/tmp/opencode/kitodo-site`):
1. `composer.json` with `typo3/cms-core|backend|frontend|fluid-styled-content|belog|install` `^13.4` plus `kitodo/presentation: dev-<branch>`; `extra.typo3/cms.web-dir: public`; a `path` repo pointing at this checkout (symlink) **and** a `github` repo for `kitodo/php-iiif-prezi-reader` (the dlf `composer.json` declares it but its tag isn't on Packagist). `minimum-stability: dev`, `prefer-stable: true`.
2. `composer install` (see gotchas below), then `php vendor/bin/typo3 setup -n --driver=sqlite --server-type=other --admin-username=admin --admin-user-password=... --project-name=...`. This creates the SQLite file, all tables, admin user.
3. `config/sites/main/config.yaml` (rootPageId, `base` matching the dev-server URL) + a `pages` row (uid 1, pid 0, doktype 1). The root/front page's `slug` must be `/` (not empty) — front-page slug routing queries `WHERE slug IN ('/')`, so an empty slug makes `/` 404 even though `?id=1` and child-page slug routes still work.
4. Frontend TypoScript via a `sys_template` record importing `fluid_styled_content` + `EXT:dlf/Configuration/TypoScript/setup.typoscript`, setting `plugin.tx_dlf.persistence.storagePid`, and defining `page = PAGE` (the dlf setup only *decorates* an existing `page` object, it does not create one — without it you get "No TypoScript object of type PAGE with typeNum=0").
5. `php vendor/bin/typo3 cache:flush`; `php -S 127.0.0.1:<port> -t public`.
6. To exercise the **PageView viewer without Solr**: add a `tt_content` row on a page with `CType='list'`, `list_type='dlf_pageview'`. The plugin reads the document from the global `tx_dlf[id]` query param (a METS or IIIF-manifest URL) and fetches it directly — no indexing/Solr needed. Put a `<form method="get"><input name="tx_dlf[id]">` on that page to let a user paste a URL.
7. The **viewer is several separate plugins**, each its own `tt_content` row on the page — `dlf_pageview` alone renders only the map. The page buttons are `dlf_navigation` (features like `pageBack`, `pageSelect`, `pageForward`, `pageLast`, `doublePage`, set via `plugin.tx_dlf_navigation.settings.features`), metadata is `dlf_metadata`, the toolbox is `dlf_toolbox` (`settings.tools`), the thumbnail strip is `dlf_pagegrid` (needs the document's `THUMBS` file group), and the TOC is `dlf_tableofcontents`. All read the same global `tx_dlf[id]`/`tx_dlf[page]` params, so **none of them need Solr or the page images** — they render even when the image host is unreachable. Plugin settings are supplied via TypoScript `plugin.tx_dlf_<name>.settings` (same mechanism as `useInternalProxy`) and override the FlexForm.
8. **Favicon**: set `page.shortcutIcon = <web-relative-path>` in the `page` TypoScript and put the file under `public/`. TYPO3 emits `<link rel="icon" href="/<path>" ...>` in `<head>` (see `cms-frontend/Classes/Http/RequestHandler.php`). The extension ships no `.ico`; derive one from `Resources/Public/Icons/Extension.svg` (e.g. `magick Extension.svg -define icon:auto-resize=64,48,32,16 favicon.ico`).

Gotchas hit during this:
- **`preferred-install: source`** (set in the site `composer.json`): GitHub dist downloads via `api.github.com/.../zipball` returned `401 Could not authenticate` while plain git/HTTPS was fine; installing from git source (composer cache) worked.
- **`vendor/composer/ClassLoader.php` vanishing**: a half-broken `vendor/` (rest of the autoloader present, `ClassLoader.php` missing) makes *every* frontend URL 500 with an empty body and `Failed opening required .../vendor/composer/ClassLoader.php` in `var/php-error.log` (before TYPO3 logging even starts). A plain `composer install` regenerates the autoloader and fixes it.
- **`useInternalProxy` / the PageViewProxy delivers 0 bytes** under TYPO3 13 + Apache/mod_php (and `php -S`): the JPEG is actually streamed to the socket (a raw-socket read shows the full `ffd8…` bytes), but the response carries a bogus `Content-Length`. Root cause is cms-frontend's `ContentLengthResponseHeader` middleware (`typo3/cms-frontend/content-length-headers`), which runs *outside* the proxy and does `$response->withHeader('Content-Length', (string)$response->getBody()->getSize())`. The proxy body is a non-seekable guzzle network stream, so `getSize()` is `null` → an **empty** `Content-Length` header; Apache rewrites that to `Content-Length: 0`, so the client reads nothing (php -S sends it literally empty). The functional tests miss this because they call the middleware `process()` directly and "don't run the middleware pipeline". **Fix: set `enableContentLengthHeader = 0` under `config` in TypoScript** (the documented kill-switch in that middleware); the server then frames via connection-close/chunked and the full image is served. (This is a test-site workaround, not an extension fix — the extension's own `copyHeaders('Content-Length')` is equally ineffective, since the middleware re-derives the value from the stream.)
- **`dlf_metadata` crashes without `settings.separator`**: the setting has no default (flexform-only). If a document has multivalued metadata, `MetadataController::buildMetaConfigObjectData()` calls `mergeMetadata($this->settings['separator'], …)` whose `$separator` param is strictly `string`, so a `null` value throws `TypeError: … must be of type string, null given` and blanks the whole page. Set `plugin.tx_dlf_metadata.settings.separator = #` (or any glue) in TypoScript. (The functional test sets it to `#` for this reason.)
- **Viewer shows no page image on an install without a theme CSS**: the OpenLayers map container `#tx-dlf-map` gets its height only from theme CSS (e.g. the UB Mannheim theme sets `height: 57em`); the dlf extension ships no stylesheet for it. Without a height the container is 0×0 and OpenLayers renders nothing, logging `No map visible because the map container's width or height are 0.` (visible in the headless-Chrome console, see below). Fixed upstream in `dlfViewer.prototype.init` (a fallback inline height when the computed height is 0). Until that lands, add a height via `page.includeCSS` in the site TypoScript, e.g. `page.includeCSS.dlfViewer = /dlf-viewer.css` with `#tx-dlf-map { height: 57em; }` in `public/dlf-viewer.css`.
- **Headless Chrome for viewer debugging** (no GUI): the page's console messages reach stderr via `"${CHROME:-/Applications/Google Chrome.app/Contents/MacOS/Google Chrome}" --headless=new --enable-logging=stderr --virtual-time-budget=25000 --timeout=35000 "URL"`; grep for `CONSOLE`. `--dump-dom` gives the post-JS DOM (the map div gets an inline `style="height: 57em;"` once the fallback runs, `ol-viewport` appears once OL initialises) and `--screenshot` renders the page (a rendered page image makes the PNG much larger than an empty map). This caught the 0×0-map issue that `curl` (headers/size only) cannot.
- **`php -S` is single-threaded**: a request that reaches *back into* the same `php -S` port (e.g. proxying a `127.0.0.1:<same-port>` URL) deadlocks it and the process dies; `lsof -iTCP:<port>` shows nothing and further requests get "Connection refused". Don't self-reference the built-in server; for Apache use a distinct port.
- When debugging HTTP framing: instrument the real flow and check `headers_list()` inside `emit()` (shows the exact header bytes PHP will send, including an empty `Content-Length:`), and capture what's actually on the wire with a small raw-socket PHP script (`stream_socket_client`, send a `GET`, read until EOF) rather than trusting `curl -o` sizes when a `Content-Length` is wrong.

- **SQLite connection key is `path`** (DBAL 4 `PDO\SQLite\Driver` reads `$params['path']`), *not* `host`/`dbname`. A wrong key silently opens an **in-memory** DB (empty `PRAGMA database_list` file) → every query is `no such table`. `setup` writes the correct `path` under `var/sqlite/`.
- **No `database:updateschema` command in v13** — the v13.4 CLI uses `typo3 setup` (from `typo3/cms-install`) to build the schema + admin + site. On a completely empty SQLite DB, *any* `typo3` command first dies in `Scheduler::__construct()` querying `tx_scheduler_task` (command discovery instantiates the scheduler). Workaround: pre-create the four tables `be_users`, `be_groups`, `tx_scheduler_task`, `be_sessions` (any minimal DDL is enough to satisfy the scheduler query) before running `setup`.
- **Port**: pick a free port — the karma/VuFind httpd on `8080` otherwise answers the requests and returns its own 404 pages.
- v13 removed `TYPO3\CMS\Core\Configuration\Environment` (now `Core\Environment`) and the `database:updateschema` command (use `setup` / `setup --force`).

## JavaScript / Webpack
- The npm project is in `Build/` (Node version from `Build/.nvmrc`): `cd Build && npm ci && npm run build|watch|test|typecheck` (jest + tsc via root `jsconfig.json`)
- JS source is `Resources/Private/JavaScript/`; the `DlfMediaPlayer` webpack entry is built from `Resources/Private/JavaScript/SlubMediaPlayer/` (name ≠ directory). Jest `moduleNameMapper` maps `lib/`, `DlfMediaPlayer/`, `SlubMediaPlayer/` to `Resources/Private/JavaScript/`
- Build outputs (`Resources/Public/JavaScript/DlfMediaPlayer/`, `Resources/Public/Css/`) are **committed to the repo by a CI bot** on push to `main`. In PRs, run the build locally to verify, but do not commit the built assets yourself

## Layout

- `Classes/` — extension code (Api, Controller, Domain, Hooks, Service, ViewHelpers, ...)
- `Configuration/` — TCA, Solr configsets, services
- `Tests/Unit`, `Tests/Functional` — mirror `Classes/` namespacing; `Build/Test/` holds PHPUnit XML + Docker setup
- `madabi/` — standalone Python metadata-analysis tool, unrelated to the extension build/tests
- `issues/` — scratch material for specific bug investigations; not part of the build

## Git

- `origin` is a personal fork; upstream is remote `kitodo` (`github.com/kitodo/kitodo-presentation`). Feature branches target `main`; older release lines are maintained on `N.x` branches (see `.github/pull.yml`)
- Commit subjects use KITODO type prefixes: `[BUGFIX]`, `[FEATURE]`, `[MAINTENANCE]`, `[TASK]`
